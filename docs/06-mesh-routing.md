# 06 — Mesh: IP-модель і маршрутизація

## 6.1 Назовні — звичайна мережа

Найважливіше рішення тут — **не вигадувати свій протокол поверх радіо**.
Вузол віддає `tun`-інтерфейс з IP-адресою, і далі працює стандартний Linux.

```
┌─ Вузол (Neptune) ────────────────────────────────────────────┐
│                                                              │
│  eth0 (на ГС) / UART+USB (на борту)                          │
│      │                                                       │
│  ┌───┴──────────────────────────────────────────┐            │
│  │              Linux IP stack                   │            │
│  │   ip route / netfilter / socket API           │            │
│  └───┬──────────────────────┬────────────────────┘            │
│      │ mesh0 (tun)          │                                │
│  ┌───┴──────────┐      ┌────┴─────┐                          │
│  │ sdrmesh-d    │      │  babeld  │  ← маршрутизація          │
│  │ (Rust)       │◄────►│          │                          │
│  │ TDMA, MCS,   │      └──────────┘                          │
│  │ ППРЧ, FEC    │                                            │
│  └───┬──────────┘                                            │
│      │ /dev/sdrmesh (kmod, DMA)                              │
│  ┌───┴──────────────────────────────────────────┐            │
│  │                   PL                          │            │
│  └───────────────────────────────────────────────┘            │
└──────────────────────────────────────────────────────────────┘
```

Наслідки, і вони всі в плюс:

- MAVLink, відео, SSH, `iperf3`, QGroundControl — працюють без жодного коду
  з нашого боку
- налагоджувати можна `ping`, `mtr`, `tcpdump`, `iperf3` — інструментами,
  яким можна вірити
- IP-адресація: `10.42.<constellation>.<node_id>/16`, статично з ID вузла
- будь-яка ГС — шлюз; `ip route` на ГС вирішує, куди йде трафік далі

> Це та сама теза, що в sdr-ground/12.4: вузол має бути **самодостатнім
> мережевим пристроєм**, а не периферією конкретної програми. Там це дало
> «будь-хто в мережі бере потік», тут дає «будь-який софт працює поверх».

## 6.2 Чому Babel

| Протокол | За | Проти |
|---|---|---|
| **Babel** | Малий, один демон у userspace, явно спроектований під лосисті і асиметричні радіоланки, приймає **зовнішню метрику**, без проблем з лічильником у петлях | Треба самим подавати метрику |
| OLSRv2 | Поширений у MANET | Важчий, чутливий до частоти HELLO |
| `batman-adv` | L2, прозорий, популярний у дронових mesh | Модуль ядра, метрика (TQ) своя і її важко підмінити нашою |
| Своє | Повний контроль | Місяці роботи, і це не те, що відрізняє продукт |

**Беремо Babel** і годуємо його метрикою з радіо. Ключ у тому, що метрика
mesh-мережі має бути **радіо-обізнаною**: кількість хопів нічого не каже про
якість.

Метрика ланки, яку `sdrmesh-d` обчислює і віддає в babeld:

$$\text{cost} = \underbrace{\frac{256}{\text{PDR}}}_{\text{втрати}} \cdot \underbrace{\frac{R_{\max}}{R_{\text{current}}}}_{\text{швидкість}} + \underbrace{C_{\text{slot}}}_{\text{ефірний час}} + \underbrace{P_{\text{flap}}}_{\text{штраф за нестабільність}}$$

- `PDR` — за фактом підтверджень від сусіда, не за власною статистикою (5.5)
- `R_current / R_max` — поточний MCS проти максимального: швидка ланка дешевша
- `C_slot` — скільки слотів ланка вже споживає: перевантажений релей дорожчає
- `P_flap` — штраф ланці, що вже кілька разів зникала. Пряма позика з
  Evaluator 3 wy-lora, і без неї маршрути будуть осцилювати

## 6.3 Де радіо і маршрутизація мусять домовлятись

Класична помилка — повісити маршрутизатор поверх радіо і вважати задачу
закритою. У TDMA-mesh вони зв'язані в двох точках:

**1. Маршрут визначає, кому потрібні слоти.** Якщо Babel вирішив, що трафік
на Борт B іде через Борт A, планувальник мусить виділити слоти
`ГС→A`, `A→B` і зворотні. Тобто карта слотів — **функція таблиці маршрутів**,
а не щось незалежне.

**2. Нові сусіди з'являються лише в beacon-слотах.** Babel не може сам
«посилати HELLO кому завгодно» — він обмежений тим, кого радіо вже чує.
Виявлення сусідів — задача шару 1 (4.3), не Babel.

Рішення: `sdrmesh-d` тримає **таблицю сусідів** як єдине джерело правди і
синхронізує її в обидва боки:

```
    beacon-слоти ──► таблиця сусідів ──► babeld (через інтерфейс/метрику)
                           ▲                      │
                           │                      ▼
                     планувальник ◄──── таблиця маршрутів
                      карта слотів
```

## 6.4 Фрагментація і MTU

Кадр у слоті 1 мс несе до ~850 мкс × (біт/с MCS). На MCS1/1 МГц це
~680 біт ≈ 85 байт. На MCS4/4 МГц — ~8160 біт ≈ **1020 байт**.

Тобто **MTU 1500 не вміщається в один слот на низьких MCS**. Потрібна
фрагментація на рівні нашого MAC (поле `flags.fragment` у 4.6):

| MCS | Корисних байт у слоті | Фрагментів на пакет 1500 Б |
|---|---:|---:|
| S (spread) | ~3 | 471 — непридатно |
| 0 | ~42 | 36 |
| 1 | ~85 | 18 |
| 2 | ~128 | 12 |
| 4 (4 МГц) | ~1020 | **2** |

Висновок, важливий для 2.2: **на низьких MCS mesh придатний для C2 і
телеметрії, але не для 1500-байтних IP-пакетів.** Лікується двома способами
одночасно:
- MSS clamping на tun (`ip link set mesh0 mtu 400` при низькому MCS, динамічно)
- агрегація кількох слотів в один логічний кадр, коли вузол має їх підряд

**Перевірка цілі 2.2 на цій арифметиці.** MCS4 у смузі 4 МГц дає 9.6 Мбіт/с
*у слоті*. Якщо ланці віддати 8 слотів із 20, стала швидкість =
9.6 × 8/20 = **3.84 Мбіт/с**. Тобто ціль «4 Мбіт/с на один хоп» досягається
саме при повному завантаженні ланки верхнім MCS — запасу немає, і це варто
пам'ятати, перш ніж обіцяти 4 Мбіт/с комусь іще в тій самій мережі.

І на spread-шарі (MCS S) IP не ходить взагалі — там тільки службовий трафік
і аварійний C2 у своєму компактному форматі. Це свідоме обмеження.

## 6.5 Кілька ГС

| Роль | Хто | Що робить |
|---|---|---|
| Time master | ГС з найкращим еталоном | Джерело епохи, централізований планувальник (5.3) |
| Gateway | **кожна** ГС | Анонсує в Babel маршрут у зовнішню мережу |
| Backup time master | решта ГС | Слухає, готова перейняти при втраті мастера |

Для зовнішнього світу кілька ГС — це кілька точок входу в одну IP-підмережу.
Babel сам розбереться, через яку ГС дешевше; на ГС `ip route` вирішує, що
робити з трафіком далі (NAT, VPN, прямий роутинг).

> [!] Дві ГС, що чують одна одну по радіо, створюють **петлю** земля↔земля,
> яка в ефірі коштує слотів, а користі не дає (у них є Ethernet). Правило:
> якщо ГС з'єднані по кабелю — радіоланка між ними отримує штраф у метриці,
> і Babel її не вибере. Потрібно явно, інакше буде марне витрачання ефіру.

## 6.6 Чого тут немає і чому

| Що | Чому не зараз |
|---|---|
| Multicast / групова передача | Beacon вже broadcast; повноцінний multicast-роутинг — фаза 6+ |
| QoS між потоками | Спершу треба, щоб один потік стабільно їхав. Потім `tc` на tun |
| Шифрування payload | Автентифікація (MIC) є з фази 1; шифрування — окреме рішення, не змінює архітектуру |
| Mobile IP / роумінг між сузір'ями | Поза скоупом |
