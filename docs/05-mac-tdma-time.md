# 05 — MAC: TDMA, слоти і час

## 5.1 Чому TDMA, а не CSMA

На десятках кілометрів CSMA ламається об фізику:

- **Приховані термінали.** Борт A і борт B не чують один одного, але обидва
  чують ГС. У CSMA вони будуть стабільно калічити одне одного на ГС.
- **Час розповсюдження.** 50 км = 167 мкс в одну сторону. Міжкадрові інтервали
  802.11 (SIFS 10–16 мкс) на таких дистанціях просто не мають сенсу.
- **Детермінізм.** C2 не терпить «коли вийде». TDMA дає гарантований слот.
- **Завадостійкість.** Слоти — це структура, яку можна прив'язати до ППРЧ.
  У CSMA прив'язувати нічого.

Атомний еталон на землі робить TDMA не просто можливим, а дешевим: не потрібно
витрачати ефірний час на постійну ресинхронізацію.

## 5.2 Суперфрейм

Довжина суперфрейму — компроміс, прямо прописаний у 2.2: вона додається до RTT
на кожному хопі.

| Довжина | RTT 2 хопи | Накладні на guard | Вердикт |
|---|---|---|---|
| 100 мс (як wy-lora) | ~200 мс | мізерні | Для C2 терпимо, для IP/TCP погано |
| **20 мс** | ~40 мс | 100 мкс / 1 мс слот = 10% | **Беремо** |
| 5 мс | ~10 мс | 100 мкс / 250 мкс = 40% | Guard з'їдає все |

**Суперфрейм 20 мс, 20 слотів по 1 мс.** На 3 вузлах PoC:

```
┌────────────────────────── Суперфрейм 20 мс ──────────────────────────┐
│ 0  │ B  │ Beacon ГС (broadcast, spread)        ← мітка часу мережі   │
│ 1  │ B  │ Beacon Борт A                                             │
│ 2  │ B  │ Beacon Борт B                                             │
│ 3  │ R  │ Request / заявки на слоти, зміни топології                 │
│ 4  │ D  │ ГС → Борт A        ┐                                      │
│ 5  │ D  │ Борт A → ГС        │                                      │
│ 6  │ D  │ ГС → Борт B        │  Data: виділяються динамічно          │
│ 7  │ D  │ Борт B → ГС        │  карта слотів приходить у beacon      │
│ 8  │ D  │ Борт A → Борт B    │                                      │
│ 9  │ D  │ Борт B → Борт A    ┘                                      │
│10..17│ D │ Вільний пул: віддається тому, кому потрібна швидкість      │
│ 18 │ S  │ Scout: зондування кандидатної частоти (2-way ping-pong)    │
│ 19 │ S  │ Scout / свіп спектра                                       │
└──────────────────────────────────────────────────────────────────────┘
```

Структура слота 1 мс:

```
├ 0      .. 850 мкс ┤ кадр (преамбула + заголовок + дані + FEC)
├ 850    .. 900 мкс ┤ запас на час розповсюдження (±150 км)
├ 900    .. 1000 мкс┤ guard: ENSM-перехід + FastLock + RF switch
```

> [!] 100 мкс guard — **припущення**. Реальні числа: FastLock <30 мкс (паспорт),
> PLL settle 20–25 мкс (гірка позика з wy-lora, проблема 7: там спершу поставили
> 2 мкс і передавали на нестабілізованій частоті), ENSM RX↔TX — [?] заміряти,
> RF switch <1 мкс. Якщо сума вийде більшою за 100 мкс — довшає слот, не
> коротшає кадр.

## 5.3 Розподіл слотів: централізовано, потім розподілено

| Фаза | Схема | Чому |
|---|---|---|
| PoC (3 вузли) | **Централізований планувальник на ГС.** Карта слотів розсилається в beacon | Детерміновано, легко дебажити, видно хто що робить |
| Продукт | Розподілена STDMA: вузли самі заявляють слоти в Request-слоті, конфлікти вирішуються хешем ID | Виживає без землі |

Централізований варіант не є тупиком: Request-слот у структурі є з самого
початку, просто на PoC заявки збирає і вирішує ГС.

**Кілька ГС → вибори мастера часу.** Мастером стає ГС із найкращим еталоном
(атомний > GNSS > кварц); при рівності — найменший ID. Решта ГС слухають і
стають шлюзами, не джерелами часу. Це пряма аналогія BMCA з PTP, і її варто
взяти як готову ідею, а не вигадувати.

## 5.4 Час: три рівні

```
      ┌─ Рубідій / CSAC на ГС ──┐
      │  10 МГц + 1 PPS          │     ±1e-11
      └────────────┬─────────────┘
                   │ PPS → GPIO → PL-таймер
                   ▼
      ┌─ PL-таймер суперфрейму на ГС ─┐
      │  лічильник епохи + мітки слотів│   джиттер ≤ 1 мкс (ціль)
      └────────────┬──────────────────┘
                   │ epoch у кожному кадрі (4.6)
                   ▼
      ┌─ DPLL на борту ────────────────┐
      │  тягне локальний таймер за      │   кварц ±0.5 ppm,
      │  часом приходу преамбули        │   але синхронізований
      └────────────────────────────────┘
```

**Чому кварцу на борту достатньо.** Дрейф ±0.5 ppm = 0.5 мкс за секунду. При
ресинхронізації щосуперфрейму (20 мс) накопичена похибка — **10 нс**, тобто
на три порядки менша за guard. Кварц на борту не є проблемою для *часу*.

Де кварц справді болить — це **частота несучої**: ±0.5 ppm на 2 ГГц = ±1 кГц,
на 4 ГГц = ±2 кГц, плюс доплер (борт 150 км/год на 2 ГГц ≈ ±280 Гц). Сума
±2.3 кГц при символьній швидкості 200 ксимв/с — це 1% від символьної
швидкості, що для carrier recovery багато, але посильно; при 4 Мсимв/с —
дрібниця. Саме тому **нижні MCS важче синхронізувати, ніж верхні**, і саме
тому преамбула розширена (4.3): кореляційний пік DSSS терпить зсув краще,
ніж фазова петля.

**Холдовер.** Якщо борт втратив землю: кварц ±0.5 ppm тримає слотову сітку в
межах ±1 мкс протягом **2 с**. Тобто вузол має ~2 с, щоб повернутись у сітку
без повторного захоплення. Понад це — rendezvous (5.6).

> [?] Якщо на бортах справді буде щось точніше за TCXO (OCXO ±10 ppb →
> холдовер ~100 с; CSAC ±1 ppb → години), це змінює 5.6 радикально: борт може
> літати в режимі радіомовчання і повертатись у сітку без захоплення.
> Варто уточнити, що саме мається на увазі під «янтарними».

## 5.5 Епоха як єдине джерело правди

Найцінніша конкретна ідея, що переноситься з wy-lora цілком (там вона
народилась із проблем 2, 4, 15, 16 — чотирьох різних багів з одним коренем):

1. **Epoch Authority.** Мастер часу — абсолютне джерело. `epoch` їде в кожному
   кадрі. Вузол, отримавши кадр, ставить `local_epoch = epoch` і більше
   нічого не вирішує сам.
2. **Усе — функція епохи.** Частота сектора, номер слота, зерно ППРЧ:
   $f = F(\text{passphrase}, \text{epoch}, \text{sector})$. Жодного локального стану.
3. **Step latch.** Частоти *не* перераховуються щосуперфрейму. Крок ротації
   = `epoch / N`, і протягом N суперфреймів частоти **нерухомі**. Без цього
   вузол, що пропустив кадр, починає скакати («проблема стрибунця»).
4. **Flywheel.** Пропустив кадр — локальна епоха +1, фаза зберігається.
   Не скидати, не чекати.

> [!] І головна порада з того ж досвіду: **ніколи не довіряти метриці, яку
> вузол порахував про себе сам.** У wy-lora був захардкоджений `"pdr": "100.0"`,
> який місяцями показував успіх при мертвому лінку. У нас PDR і PER
> вимірюються **за фактом отриманих підтверджень від сусіда**, і жодна
> метрика не має права бути константою в коді. Див. 11.4.

## 5.6 Первинне захоплення (rendezvous)

Вузол знає лише пас-фразу сузір'я. З неї детерміновано виводиться:

- `network_id` (щоб не плутати сузір'я)
- список **16 опорних частот rendezvous**, рівномірно по всьому вікну
  (4 на сектор) — конкретні значення залежать від профілю діапазону, тому
  в rendezvous-beacon профіль передається повністю, а не хешем
- зерно ППРЧ робочої сітки

```
Старт борта
   │
   ├─ сканує 16 опорних частот, по 50 мс кожна  (≤ 0.8 с на цикл)
   │     ↑ слухає spread-шар, тобто чує на −14 дБ SNR
   │
   ├─ почув SYNC_BEACON → витягує epoch, профіль, карту слотів
   │
   └─ переходить у робочу сітку, заявляє свої слоти в Request-слоті
```

**Fallback.** Втрата зв'язку > 50 суперфреймів (1 с) → вузол повертається на
опорні частоти, але **продовжує крутити flywheel**, щоб при поверненні
епоха вже збігалась.

Для бортів fallback має ще один рівень: якщо землі не чути, борт пробує
**інших бортів** (вони теж передають beacon у своїх слотах) — це і є точка,
де mesh починає працювати на користь синхронізації, а не лише трафіку.

## 5.7 ППРЧ у межах вікна

| Параметр | Значення |
|---|---|
| Секторів | 4, рівномірно по вікну, рознос центрів ≥250 МГц (3.5) |
| Зміна сектора | **на межі суперфрейму** (через калібрування, 3.6) |
| Стрибки всередині суперфрейму | у межах сектора, FastLock-профілями |
| Ротація | шахова: за раз міняється один сектор із чотирьох |
| Період ротації | 2–3 с (конфігурується) |
| Куди стрибає | на переможця голосування за якість частоти (07.4) |

Шахова ротація — ще одна позика з wy-lora, і логіка та сама: поки один сектор
перестроюється, решта працює, тож ротація **ніколи не є перервою зв'язку**.
Різниця лише в тому, що там 4 сектори працювали одночасно на 4 паралельних
каналах, а тут вони чергуються в часі.
